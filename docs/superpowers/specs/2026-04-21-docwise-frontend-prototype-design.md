## 背景

当前 `Docwise` 已经出现了较清晰的产品方向：

- `docwise/app/layouts/default.vue` 已切到统一 shell
- `docwise/app/components/shell/DocwiseConversationRail.vue` 承担左侧全局对话位
- `docwise/app/components/shell/DocwiseFocusHeader.vue` 承担右侧监看区头部
- `docwise/app/pages/projects/index.vue` 已把入口收敛到项目中心
- 旧 `/workspace` 页面已不再适合作为产品主入口

但真实后端能力、工作流数据、执行流反馈、文件结果链路还未形成稳定产品面。继续补后端会放大方向不确定性，也会掩盖前端信息架构是否成立这个更早期的问题。

因此当前阶段应先把 `Docwise` 做成一个可演示、可点击、可验证的前端核心原型，再决定后端完整实现顺序。

## 目标

- 验证 `Docwise` 的产品壳层是否成立：左侧指挥、右侧监看
- 验证从项目入口到跨项目总览，再到单项目详情的导航是否顺畅
- 验证项目详情的核心业务分区是否应固定为 `总览 / 蓝图 / 任务 / 审议 / 产出`
- 验证焦点上下文在左侧和右侧之间的联动是否清晰可理解
- 用 mock 数据演示关键状态变化，而不是依赖真实后端联调

## 非目标

- 不接真实 Rust / Tauri 后端命令
- 不接真实数据库
- 不做真实文件读写
- 不做真实 agent 流式执行
- 不做真实 Markdown 预览或文档编辑
- 不做完整执行引擎、审议处理或产出落盘逻辑

## 产品定位

`Docwise` 当前原型阶段不是“工作台功能页集合”，也不是“内置编辑器”。

它应被定义为：

- 左侧是全局对话与指挥位
- 右侧是跨项目或单项目的监看区
- 用户通过导航和焦点切换理解系统状态
- 真实执行、写盘、审议恢复等复杂能力暂时只用 mock 状态表达

这意味着前端原型要优先验证“信息架构和交互叙事”，而不是“功能是否真跑通”。

## 方案比较

### 方案一：壳层优先

先把 `/projects`、`/projects/overview`、`/projects/:id` 做成完整可点击原型，所有业务数据来自 mock。

优点：

- 最快验证产品长相
- 最适合当前仓库已有页面骨架
- 能尽快确认导航、层级、焦点、分屏结构

缺点：

- 业务真实性较弱
- 后续接真状态机时需要替换数据来源

### 方案二：流程优先

优先做“蓝图 -> 任务 -> 执行 -> 审议 -> 产出”一条假流程，页面壳层只保留最低限度。

优点：

- 更贴近 agent 工作流叙事
- 更容易暴露业务链路缺口

缺点：

- 可能过早滑回后端思维
- 壳层与导航问题会被延后暴露

### 方案三：混合最小闭环

同时做完整壳层和一条可走通的最小业务流程，但只覆盖一个项目样本。

优点：

- 展示完整度更高
- 更容易向外演示

缺点：

- 容易范围膨胀
- 在当前阶段会稀释对信息架构本身的验证

### 推荐

采用**方案一：壳层优先**。

理由：当前仓库已经开始向统一 shell 收敛，最需要尽快确认的是产品壳层、导航关系、焦点模型和页面分区，而不是后端真链路。等壳层稳定后，再挑一条最小流程补入即可，返工最少。

## 原型范围边界

### 要做的范围

- 项目中心页
- 跨项目总览页
- 单项目详情壳页
- 单项目详情下的 `总览 / 蓝图 / 任务 / 审议 / 产出` 五个 tab
- 左侧全局对话位中的当前焦点展示
- 关键空态、加载态、错误态
- 基于 mock 数据的可点击交互

### 不做的范围

- 后端命令联调
- 实际工作区扫描
- 实际文件系统写入
- 实际执行日志流
- 实际人工审议提交
- 实际产出文件打开与预览

边界原则只有一条：**只验证“怎么用、怎么走、怎么看”，不验证“怎么真实落地”。**

## 信息架构

### 总体结构

推荐固定为两栏壳层：

- 左侧：全局对话与控制塔
- 右侧：业务监看与详情内容

不再恢复旧 `workspace` 工作台模型，也不新增第三套并行导航。

### 左侧区域

左侧承担全局控制语义，应稳定包含：

- 全局定位说明
- 当前焦点摘要
- 核心快捷入口
- 最近项目或最近任务摘要
- 当前动作建议或下一步提示

左侧不是第二套业务详情区，不承载大量列表与编辑表单。

### 右侧区域

右侧承担所有业务内容表达，分成两层：

- 跨项目层：`/projects/overview`
- 单项目层：`/projects/:id`

单项目层下再用 tab 切换五个稳定视图：

- `总览`
- `蓝图`
- `任务`
- `审议`
- `产出`

### 导航规则

- `/projects` 负责登记、管理、打开项目
- `/projects/overview` 负责跨项目监看
- `/projects/:id` 负责某个项目的局部监看
- `/workspace` 只保留跳转兼容，不再承担主业务语义

## 页面设计

### 项目中心

定位：项目入口管理页。

应支持：

- 新增假项目
- 分组展示项目
- 展示工作区路径
- 打开项目
- 删除项目
- 表达最近访问或最近打开语义

成功标准：用户能够从这里进入后续全部原型链路。

### 跨项目总览

定位：管理层视角首页。

建议展示：

- 项目总数
- 运行中任务数
- 待审议数
- 最近产出
- 最近活动时间线
- 需要优先关注的项目卡片

信息数量应克制，避免变成“仪表盘墙”。

### 单项目详情

定位：右侧聚焦态，不是新的应用根。

进入后：

- 左侧保持不动
- 右侧切为该项目详情
- 顶部显示项目名称、当前 tab、关键状态摘要

### 项目详情 Tabs

#### 总览

展示：

- 项目阶段
- 项目健康度
- 最近活动
- 风险提示
- 当前主任务摘要

#### 蓝图

展示：

- 蓝图列表
- 当前生效蓝图
- 蓝图状态标签
- 蓝图摘要与边界说明

#### 任务

展示：

- 任务树或按状态分组列表
- 当前进行中任务
- 被阻塞任务
- 最近一次执行摘要

#### 审议

展示：

- 待处理审议项
- 审议类型标签
- 风险等级
- 推荐下一步动作

#### 产出

展示：

- 文档产出列表
- 最近更新时间
- 产出摘要
- 文件类型或路径提示

每个 tab 至少要有“列表 + 摘要”两层，不做单纯装饰卡片。

## 最小交互闭环

原型必须能够完整演示以下脚本：

1. 进入项目中心
2. 新增一个假项目
3. 打开项目后进入跨项目总览
4. 从总览进入某个项目详情
5. 在 `总览 / 蓝图 / 任务 / 审议 / 产出` 间切换
6. 点击某个任务后，左侧焦点同步变化
7. 返回跨项目总览后，仍能看到该项目最近活动

如果这条脚本流畅，说明前端核心原型已经成立。

## Mock 数据策略

原型不应把假数据散落在页面内部，而应建立一层前端 fake domain。

建议至少准备以下 mock 集合：

- `mockProjectCatalog`
- `mockOverviewStats`
- `mockProjectDetail`
- `mockBlueprints`
- `mockTasks`
- `mockReviews`
- `mockOutputs`
- `mockActivityFeed`

同时保留最小前端状态容器：

- `selectedProjectId`
- `selectedTaskId`
- `currentWorkspaceId`

要求：mock 字段命名尽量贴近现有领域模型，避免未来接后端时整页重写。

## 焦点联动

原型里最关键的交互不是按钮多少，而是焦点是否清楚。

焦点联动原则：

- 右侧切项目，左侧 `projectId` 跟着变
- 右侧点任务，左侧 `taskId` 跟着变
- 返回跨项目总览时，项目级焦点可清空或退回最近焦点，但规则必须一致
- tab 切换不应丢失当前项目焦点

这部分决定“左侧全局对话 + 右侧监看区”是否真正成立。

## 状态设计

原型至少要表达四类状态：

- 空态：尚无项目、尚无蓝图、尚无任务、尚无产出
- 加载态：页面首次加载、切换详情、切换 tab
- 错误态：数据获取失败、焦点无效、项目不存在
- 过程态：未开始、进行中、待审、已产出

空态必须告诉用户下一步动作，不能只是空白占位。

## 风险与应对

### 风险一：原型变成静态海报

应对：每页至少有一个主操作、一个状态变化、一个返回链路。

### 风险二：范围重新滑回后端实现

应对：原型阶段所有页面禁止直连真实 `invoke`，统一走 mock adapter。

### 风险三：跨项目总览信息过载

应对：总览只保留 4 到 6 个关键模块，其余细节留到项目详情。

### 风险四：项目详情 tab 太空

应对：每个 tab 都必须承载可解释的业务对象，而不是只放视觉占位。

### 风险五：未来真数据接入成本高

应对：mock 模型命名贴近 `project / blueprint / task / review / output` 领域对象，并把页面与数据源解耦。

## 最小验收标准

完成原型后，应满足以下验收：

- 能从项目中心开始完整演示一次核心路径
- 能清楚体现左侧指挥、右侧监看的产品心智
- 能说明跨项目与单项目两层视角的差异
- 能说明五个项目详情 tab 的边界
- 能在不依赖后端的情况下稳定展示主要状态变化

只要这些成立，就可以进入下一阶段 implementation plan，再决定哪些点需要优先接真实后端。

## 实施顺序建议

1. 固定路由骨架与页面层级
2. 抽离 mock domain 数据层
3. 完成跨项目总览页
4. 完成单项目详情壳与 tab
5. 完成焦点联动
6. 补齐空态、加载态、错误态
7. 最后再评估后端接入优先级
