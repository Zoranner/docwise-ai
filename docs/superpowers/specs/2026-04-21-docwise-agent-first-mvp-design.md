# Docwise Agent-First MVP 设计

| 属性 | 说明 |
|------|------|
| 状态 | 已讨论待评审 |
| 日期 | 2026-04-21 |
| 范围 | `docwise` v0 主业务流程收敛 |
| 目标 | 先验证“项目 -> 蓝图 -> 任务 -> 智能体执行 -> 文档落盘”闭环，不以内置文件可视化为前提 |

## 背景

当前 `Docwise` 已经具备工作区宿主、项目数据库、蓝图/任务命令、智能体流式回合等核心骨架，但产品形态仍混杂了工作台、编辑器、预览器和调试面板。与此同时，真实预览链路仍未接通：

- 应用内预览仍是 `ComrakStubBackend`
- `mdweave + blockplot` 的真实渲染和 sidecar 尚未进入可用状态
- 内置文件编辑和预览并不是试用主流程的决定性能力

因此，v0 的目标不应是继续补文件展示，而应是把主业务流程收敛成一个可试用、可观测、可验证的“文档生产指挥台”。

## 目标

- 让用户以规划者、管理者、指挥者的身份管理多个文档项目
- 让用户通过全局对话驱动智能体生成蓝图、派生任务并推进执行
- 让智能体能够直接写入工作区中的 Markdown 文件
- 让用户通过右侧监看区理解项目状态、任务推进、人工介入事项和文档产出
- 把文件查看、编辑、预览交给 VSCode 等外部工具，避免阻塞主业务验证

## 非目标

- 不做应用内 Markdown 原文查看
- 不做应用内 Markdown 预览
- 不做 DOCX 导出作为 v0 试用前提
- 不做 Mermaid / Vega-Lite / Draw.io 渲染作为 v0 试用前提
- 不把 `Docwise` 做成一个内置 IDE 或内置文档编辑器

## 产品定位

`Docwise` v0 不是“文档编辑器”，而是“AI 驱动的文档项目指挥台”。

用户不是进入某个项目逐字逐句写文档，而是：

- 维护一组项目
- 指挥智能体为项目搭建蓝图
- 让智能体基于蓝图规划并执行任务
- 在关键卡点上做人工介入
- 通过外部编辑器查看和修正文档结果

这决定了产品壳层应采用：

- 左侧常驻全局对话
- 右侧上下文监看区
- 全局总览与项目钻取并存

而不是“聊天页 / 编辑页 / 预览页”平级切换。

## 核心闭环

v0 需要优先验证的闭环只有一条：

`项目 -> 蓝图 -> 任务 -> 执行 -> 文档落盘 -> 人工校正`

更具体的流程为：

1. 用户登记并打开项目
2. 用户在左侧对话中描述目标
3. 智能体创建或更新蓝图
4. 用户批准蓝图
5. 智能体派生任务并开始执行
6. 智能体直接写入工作区文件
7. 若执行受阻，系统创建人工介入对象并等待处理
8. 用户在外部工具中查看结果，并在需要时继续通过对话干预

试用成功标准不是“预览好不好”，而是“用户能否在短时间内完成一次真实文档落盘闭环”。

## 领域术语

`Docwise` 需要一套内外一致的 canonical 术语。产品设计、界面文案、前端状态、后端模块、接口命名、数据库模型、事件命名都应沿用同一套名称。

### 主业务对象

| 中文 | 英文 | 定义 |
|------|------|------|
| 项目 | `Project` | 一项持续推进的文档工作范围，是用户管理与观察的顶层业务对象 |
| 蓝图 | `Blueprint` | 项目的目标体系、结构边界与约束，是任务规划的真相来源 |
| 任务 | `Task` | 为落实蓝图而拆解出的执行单元，可树状组织 |

### 执行与协同对象

| 中文 | 英文 | 定义 |
|------|------|------|
| 执行 | `Run` | 某个任务的一次具体执行实例 |
| 审议 | `Review` | 因信息缺失、方向冲突、越界或待确认而触发的人工处理事项 |
| 产出 | `Output` | 任务或执行产生的结果记录，如文件路径、摘要、引用等 |
| 会话 | `Session` | 用户与智能体团队持续交互的上下文空间 |

### 运行机制对象

| 中文 | 英文 | 定义 |
|------|------|------|
| 工作区 | `Workspace` | 文件系统根目录与宿主运行上下文，不等于业务上的项目定义 |
| 快照 | `Snapshot` | 文件写入前后的内容留档 |
| 锁 | `Lock` | 防止并发写入冲突的占用记录 |
| 事件 | `Event` | 系统状态变化的发布记录 |
| 指令 | `Command` | 对系统发出的明确动作请求 |

### 命名约束

- 同一概念只允许一个 canonical 名称
- `Project / Blueprint / Task / Review / Output` 不允许再有第二套同义术语
- `blocked` 只能用作状态或关系，不能用作对象名
- 不再使用 `Checkpoint` 作为人工介入对象名
- 不再使用 `Artifact` 作为用户可见的结果对象名

## 领域关系

推荐关系如下：

- `Project 1 - N Blueprint`
- `Blueprint 1 - N Task`
- `Task 1 - N Run`
- `Task 0 - N Review`
- `Task 0 - N Output`
- `Run 0 - N Output`
- `Project 1 - 1 Workspace` 作为 v0 建议约束

这里保留一个明确假设：

- **v0 假设一个 `Project` 对应一个主要 `Workspace`**

这样可以最大限度降低宿主复杂度和文件写入边界复杂度。  
如果后续出现跨多个目录协同的强需求，再把 `Project - Workspace` 放宽为 `1 - N`。

## 审议语义

`Review` 不是普通的流程检查位，而是“执行被挂起，等待人工处理后继续”的对象。

它的出现条件包括但不限于：

- 缺少继续执行所需的关键信息
- 当前方案与蓝图边界冲突
- 需要用户拍板决定方向
- 执行结果风险过高，需要人工复核

因此推荐语义为：

- `Task.status = blocked`
- `Task` 或 `Run` 由某个 `Review` 阻塞
- `Review` 被处理后，对应任务恢复推进

这比用 `Checkpoint` 更符合该对象的真实职责，也更利于后续扩展到审批、补料、裁决等不同类型。

## 信息架构

### 壳层结构

推荐采用三段式壳层：

- 顶部：全局导航与当前焦点
- 左侧：常驻对话区
- 右侧：上下文监看区

### 顶部区域

顶部区域承担全局导航和当前态势表达，应至少包含：

- 应用名称与当前模式
- 项目切换入口
- 全局总览入口
- 待处理审议入口
- 当前焦点面包屑

顶部区域不承载复杂业务操作，主要负责“我现在在看哪里”。

### 左侧对话区

左侧对话区是全局控制面，不隶属于单个项目页面。

其职责是：

- 接收用户面向所有项目的规划与指挥
- 支持围绕当前焦点发起局部指令
- 承载规划智能体与执行智能体的持续会话
- 暴露需要用户介入的审议事项

左侧对话的默认语义是“全局会话”，但它应感知右侧当前焦点，在生成消息时自动带上相关上下文：

- 在全局总览下，对话默认讨论整体优先级和跨项目推进
- 在项目视图下，对话默认绑定该项目
- 在蓝图视图下，对话默认绑定该蓝图
- 在任务视图下，对话默认绑定该任务

### 右侧监看区

右侧区域是内容监看区，不承担文档编辑职责。

默认首页为全局总览，主要展示：

- 项目列表与状态分布
- 蓝图与任务规模
- 待处理审议队列
- 最近执行与产出动态

选择单个项目后，右侧进入项目详情视图。项目详情推荐使用 Tabs 组织：

- `总览`
- `蓝图`
- `任务`
- `审议`
- `产出`

这些 Tab 分别对应：

- `总览`：项目状态总貌、风险、最近活动
- `蓝图`：蓝图列表、详情、状态、约束、审批动作
- `任务`：任务树、执行状态、当前阻塞、最近运行记录
- `审议`：待处理与已处理人工事项
- `产出`：已写入文件、结果摘要、最近更新时间、外部打开入口

## 页面建议

### 全局总览

全局总览是默认落地页，定位是“运营台首页”。

它应回答五个问题：

- 现在有多少项目在推进
- 哪些项目需要优先关注
- 哪些蓝图尚未批准
- 哪些任务正在运行或被阻塞
- 哪些审议正在等待用户处理

### 项目详情

项目详情不是新的应用根，而是右侧的聚焦态。

进入项目详情后：

- 左侧对话保持常驻，不切走
- 右侧切换为该项目的局部监看视图
- 顶部面包屑清楚显示当前项目与当前 Tab

### 蓝图视图

蓝图视图应优先支持：

- 创建蓝图
- 查看蓝图结构与约束
- 比较不同蓝图状态
- 执行批准、归档、替代等动作

蓝图不是任务表，也不是排期页，应保持“结构与边界真相”的角色。

### 任务视图

任务视图应优先支持：

- 树状浏览任务
- 查看任务状态与优先级
- 查看任务最近执行
- 从任务跳转到相关审议和产出

任务视图不承担文件正文浏览。

### 审议视图

审议视图需要成为用户处理人工介入事项的统一入口。

它至少要支持：

- 列出待处理审议
- 查看触发原因、关联任务、关联执行
- 记录处理结果
- 让被阻塞任务恢复推进

### 产出视图

产出视图是 v0 中替代“应用内预览”的关键界面。

它至少需要展示：

- 产出类型
- 文件相对路径与绝对路径
- 产出摘要
- 关联任务 / 执行
- 最近更新时间
- 外部打开入口

用户在这里不看正文，只确认“系统写了什么、写到哪里、最近发生了什么”。

## MVP 裁剪

### 后端保留

- `workspace/`：收敛为宿主管理能力
- `project/`：作为主业务核心，承载 `Project / Blueprint / Task / Review / Output`
- `execution/`：作为主业务骨架，继续承载规划流、执行流、工具调度和事件流
- `catalog/`：管理项目清单与打开入口
- `state/`：维护全局焦点与项目上下文

### 后端退出关键路径

- `preview/`
- `mdweave` 的可视化预览能力
- `blockplot` 的 sidecar 渲染能力
- `mx2svg` 的图形渲染能力

这些模块可以继续存在，但不再阻塞 v0 主流程。

### 前端保留

- 项目中心
- 全局总览
- 项目详情壳层
- 左侧全局对话
- 蓝图 / 任务 / 审议 / 产出监看视图

### 前端退出关键路径

- 应用内 Markdown 编辑器
- 应用内 Markdown 预览器
- 文件正文读取与保存交互
- 当前 `workspace/index.vue` 中面向调试的 JSON 面板和混合工作台结构

## 技术收敛建议

### 上下文模型

现有 `ActiveContext` 需要从围绕 `filePath` 的模型，收敛成围绕“监看焦点”的模型。

推荐方向：

```ts
type FocusContext = {
  projectId: string | null
  blueprintId: string | null
  taskId: string | null
  reviewId: string | null
  outputId: string | null
}
```

`Workspace` 仍由宿主层维护，但不再成为 UI 视角的第一焦点。

### 模块命名

前后端模块建议逐步向 canonical 名称对齐：

- `checkpoint` -> `review`
- `artifact` -> `output`
- `task_runs` 可以保留，但业务命名统一为 `Run`

允许在迁移阶段出现兼容层，但目标名称需要明确且唯一。

### 事件命名

事件命名也应改成同一套术语，例如：

- `project_changed`
- `blueprint_approved`
- `task_blocked`
- `review_opened`
- `review_resolved`
- `output_recorded`

## 风险

### 风险一

如果壳层还继续保留编辑器和预览器心智，团队会不断把时间投入到文件可视化，而不是主业务闭环。

### 风险二

如果术语系统不尽快收敛，后续会同时出现 `checkpoint / review / blocker`、`artifact / output` 等多套叫法，导致维护成本快速上升。

### 风险三

如果 `Project` 和 `Workspace` 的边界不提前定清，UI 焦点、数据库绑定和文件写入边界会不断冲突。

## 验收标准

满足以下条件即可认为 v0 的产品方向成立：

- 用户能创建并切换多个项目
- 用户能通过对话创建和批准蓝图
- 智能体能基于蓝图生成并推进任务
- 智能体能直接写入工作区文件
- 用户能在右侧清楚看到任务推进、阻塞和产出
- 用户能通过外部工具查看和修正文档
- 整个过程不依赖应用内预览能力

## 后续演进

当 v0 跑通后，再考虑以下能力进入下一阶段：

- 应用内文件可视化
- `mdweave` 真预览替代 stub
- `blockplot` 图形渲染接入
- 更丰富的项目间运营视图
- 更细粒度的审议类型体系

在此之前，所有可视化工作都不应反向定义主业务壳层。
