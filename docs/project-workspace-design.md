## 标准定位

本文是当前 `docwise` 前端的**信息架构标准**。

它负责回答：

- 三列分别是什么
- 项目、对话、工作区如何组织
- 右侧标签集合是什么
- 页面和壳层如何路由与切换

它不负责视觉 token、配色、阴影、圆角和基础部件外观，这些以 [`visual-system-design.md`](./visual-system-design.md) 为准。

## 背景

当前 `docwise` 前端原型已经从早期的 editor-first、全局会话、五标签项目页等多套互相冲突的结构中收敛出来。现行方案必须回到以下基本事实：

- `Docwise` 是本地软件，不是网页站点
- `Project` 是顶层业务容器
- 对话归属于具体项目，而不是全局漂浮群聊
- 右侧不是单一静态视图，而是当前项目下的结构化工作区
- `蓝图` 与 `任务` 不能被画成一棵混合树，必须尊重真实领域关系

## 目标

- 固定主壳层为三列：项目列表、项目对话、项目工作区
- 让“一个项目一个独立对话框”成为默认语义
- 让右侧工作区固定为 `蓝图 / 任务 / 日志` 三个一级标签
- 让蓝图、任务、日志各自承担单一职责，不再互相污染
- 在前端原型阶段允许使用 mock 数据，不依赖后端联调

## 非目标

- 不处理后端接口、数据库、执行引擎接线
- 不处理真实文件编辑、预览、导出
- 不继续保留 `总览 / 审议 / 产出` 五标签结构
- 不继续维护“全局会话”或“恢复会话”的旧心智

## 领域真值对齐

前端必须严格遵守 [`product-design.md`](./product-design.md) 中的对象关系：

- `Project` 是业务顶层容器
- `Blueprint` 属于 `Project`
- `BlueprintItem` 属于 `Blueprint`
- `Task` 通过 `tasks.blueprint_item_id` 归属到某个 `BlueprintItem`
- `Task` 通过 `tasks.parent_id` 形成自己的树状结构

因此真实关系应表达为：

`Project -> Blueprint -> BlueprintItem -> 根任务 -> 子任务树`

这意味着：

- 任务不是蓝图本体的直接子节点
- 蓝图页不能直接把任务混排进蓝图目录里
- 任务页必须围绕“当前蓝图条目”展开，而不是围绕“整个项目的散乱任务列表”展开

## 壳层决策

### 总体布局

主界面固定为三列工作区：

- 第一列：项目列表
- 第二列：当前项目对话框
- 第三列：当前项目工作区

这是产品的长期壳层，不再回到“左侧聊天 + 右侧单页内容”的二段式，也不保留网页式标题栏。

### 第一列：项目列表

第一列是常驻项目导航，不是总览仪表盘。

应承担的职责：

- 显示活动项目列表
- 显示项目名称、阶段、进度百分比
- 标记当前前台项目
- 承载项目切换入口

不应承担的职责：

- 不展开蓝图列表
- 不展开任务树
- 不承载聊天内容
- 不承担右侧工作区摘要替身

### 第二列：项目对话框

第二列是当前项目的独立会话，不是全局会话。

应承担的职责：

- 展示当前项目的连续消息流
- 支持围绕当前项目持续输入
- 展示与当前项目有关的系统消息、规划回复、执行回复

应明确禁止的表达：

- 不出现“全局群聊”
- 不出现“恢复历史会话”
- 不出现项目无关的混杂消息流

项目切换时，第二列跟随切换到目标项目自己的消息流；每个项目保留独立的消息历史和输入上下文。

### 第三列：项目工作区

第三列承载当前项目的结构化工作区，并固定为三个一级标签：

- `蓝图`
- `任务`
- `日志`

第三列顶部不再保留额外的项目摘要头部。项目身份已经由第一列和第二列锁定，右侧应直接进入页签内容本身。

## 标签职责

### 蓝图

蓝图页负责表达项目的规划真相，而不是执行细节。

应展示：

- 当前项目下的蓝图对象
- 蓝图状态
- 蓝图目标、受众、约束
- `BlueprintItem` 纵向目录
- 当前选中条目的详细说明

表达规则：

- 蓝图条目必须纵向排列
- 不使用横向卡片平铺整个条目集合
- 默认支持十几到几十项连续滚动

### 任务

任务页负责表达执行结构，而不是重新展示蓝图目录。

应展示：

- 当前选中 `BlueprintItem`
- 该条目对应的根任务
- 根任务下的子任务树
- 节点状态、局部完成度、阻塞原因、待决策项

表达规则：

- 任务页默认围绕某个当前蓝图条目展开
- 不把整个项目所有任务简单平铺成一列
- 不把蓝图和任务混成一棵父子树

### 日志

日志页负责承接当前项目的事件流与时间线。

应展示：

- 蓝图创建、修改、批准、重新批准
- 任务创建、开始、完成、失败、阻塞、恢复
- 检查点或人工决策开启与关闭
- 产出更新
- 项目进度变化

日志页只负责可追踪性，不承担蓝图详情或任务树浏览职责。

这里的“日志”是项目级事件流视图。领域层仍然可以存在 `review`、`output` 等对象，但在当前前端信息架构里，它们通过日志事件、任务详情或后续细部面板承接，不单独升级为与 `蓝图 / 任务 / 日志` 并列的一级标签。

## 关键交互规则

### 项目切换

当用户切换项目时：

- 第一列更新当前前台项目高亮
- 第二列切换到该项目独立消息流
- 第三列保留当前标签类型，但内容切换到目标项目

如果目标项目尚无数据，第二列和第三列应出现项目级空态，而不是退回全局空白页。

### 蓝图与任务联动

蓝图与任务之间需要有明确但克制的联动：

- 蓝图页选择某个 `BlueprintItem`
- 当前条目成为项目级工作区焦点
- 任务页基于该条目展示任务树

联动边界如下：

- 左侧对话不因右侧切换而丢失项目归属
- 右侧标签切换不改变当前项目
- 日志页不自动跟随聊天内容变化

### 项目进度

项目进度百分比是项目层字段，不属于蓝图、任务或日志任一单标签。

前端表达规则：

- 第一列项目列表必须展示
- 第二列可轻量展示
- 第三列不再通过顶部摘要重复展示

## 路由约定

当前前端主入口已经收敛到项目化工作区模型：

| 路由 | 用途 |
|------|------|
| `/` | 跳转到当前项目页 |
| `/projects` | 跳转到当前项目页 |
| `/projects/:id` | 当前主业务入口 |
| `/projects/overview` | 历史兼容跳转 |
| `/workspace` | 历史兼容跳转 |

因此 `/workspace` 不再表示独立“编辑器工作台”，而只是旧路由兼容层。

## 前端结构约定

当前壳层对应的前端结构应理解为：

| 路径 / 模块 | 职责 |
|-------------|------|
| `app/layouts/default.vue` | 应用总壳层 |
| `app/components/project/ProjectRail.vue` | 第一列项目列表 |
| `app/components/shell/ConversationRail.vue` | 第二列项目对话框 |
| `app/components/workspace/WorkspacePanel.vue` | 第三列项目工作区 |
| `app/components/workspace/*.vue` | 蓝图、任务、日志子面板 |
| `app/pages/projects/[id].vue` | 当前项目主页面 |

## 结果标准

当这一轮前端重构完成后，原型必须能稳定表达以下使用心智：

- 用户先看到的是项目，而不是抽象功能导航
- 每个项目拥有独立对话，不再共享全局消息流
- 右侧工作区只围绕当前项目展开
- 蓝图、任务、日志三者职责单一且边界清晰
- 信息架构不再回退到 editor-first 或全局会话模型
