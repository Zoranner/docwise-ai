## 标准定位

本文是 `docwise` 当前前端界面的**视觉标准**。

它负责回答以下问题：

- 主题方向是什么
- 三列桌面壳层应呈现何种材料感与层级感

它不负责重定义产品对象关系，也不单独决定前端信息架构。当前文档边界如下：

- 领域模型与对象关系，以 [`product-design.md`](./product-design.md) 为准

## 文档目的

本方案用于重新定义 Docwise 前端的视觉语言与界面外观，解决当前原型存在的以下问题：

- 界面整体呈现网页化、轻飘、松散的视觉倾向，不符合本地桌面软件应有的器物感与工作台感
- 面板、列表、标签、输入区之间缺乏统一的明暗关系、材质关系与节奏关系
- 间距、圆角、边框、阴影、色阶与状态表达缺少统一标准，导致不同区域像来自不同系统
- 视觉设计越界影响功能心智，出现以“重定义对话语义”替代“重设计界面样式”的偏差

本方案的目标不是修补现有页面，而是在不改动产品功能定义与信息架构前提下，彻底重建一套稳定、可执行、可复用的桌面视觉体系。

## 设计边界

### 保持不变的部分

- 应用仍为单页桌面软件
- 主界面仍为三列结构：项目栏、对话框、工作区
- 工作区仍以 `蓝图 / 任务 / 日志` 三个标签页组织
- 第二列仍然是项目专属对话框，不改变其产品语义与交互定位

### 本次重设计覆盖的部分

- 全局主题与色彩体系
- 明暗层级与材质关系
- 阴影、高光、边框与表面压感
- 栅格、间距、圆角、文字与布局节奏
- 项目栏、对话框、标签页、列表、详情区、输入区的统一外观规则
- 基础界面部件的统一视觉规范

### 本次重设计不处理的部分

- 后端数据来源与接口
- 蓝图、任务、日志的业务逻辑
- 对话框的功能语义、消息归属与工作流
- 编辑器、预览器、文件写入策略
- 浅色模式

### 主题模式声明

本次重设计仅处理深色模式。浅色模式不在当前范围内，亦不作为验收目标。所有色板、阴影、对比度、滚动条与焦点环规则，均以深色桌面主题为前提。

## 设计目标

### 桌面化

界面必须呈现明确的本地软件质感，而非浏览器页面质感。用户打开应用后，应感知到一个稳定、厚实、可操作的工作台，而不是由若干卡片与网页分区拼合而成的视图。

### 系统化

所有视觉表现必须从同一套规则生长出来。任何一个区域的样式都必须能被解释为“同一系统中的不同用途”，而不是 page-local 的临时表达。

### 高密度

Docwise 面向持续工作的桌面场景，界面应允许较高的信息密度。高密度并不意味着拥挤，而意味着在有限空间内以精确节奏承载更多稳定信息。

### 重质感

界面必须具备明确的表面关系、材质关系与层级压感。阴影、内高光、边框与底色变化不是装饰，而是构建桌面器物感的核心手段。

### 不越界

视觉重构不得改写产品定义。对话框仍是对话框，标签页仍是标签页，项目栏仍是项目栏。样式体系服务于功能表达，而不是替代功能定义。

## 视觉哲学

### 工作台而非网页

整页界面应被视为一个连续的工作台。左侧项目栏、中间对话框、右侧工作区共享同一套机身语言、材质语言与边界语言。它们是同一台设备上的三个功能区，而不是三个独立网页模块。

### 质感来自材料关系

桌面效果不应依赖单一颜色或大面积渐变，而应通过以下关系共同建立：

- 外层机身与内部面板的明暗对比
- 面板浮起时的投影与边缘高光
- 选中项与非选中项的压感差异
- 工作区标签抬起与沉下的层级关系
- 输入区、列表区、详情区表面粗细不同的材质区分

### 稳定先于炫技

视觉风格可以强，但必须稳定。界面需要显得有力量、有器物感，而不是依赖高饱和色、强发光、复杂纹理和过度动效制造“设计感”。

### 暖金属而非默认科技蓝

主题主调不采用常见的蓝灰 SaaS 风格，也不沿用 Nuxt UI 默认的冷蓝技术感。Docwise 的视觉主调应采用“石墨机身 + 暖金属强调”的方向，使其更贴近本地工作软件而非浏览器产品。

## 主题方向

### 总体方向

本方案采用如下主题气质：

- 机身基调：石墨黑
- 面板材质：磨砂金属
- 主强调色：琥珀铜
- 正文文字：暖灰白
- 状态表达：低饱和功能色

该方向用于建立“厚重、稳定、克制、具有桌面质感”的总体印象。

### 基础色板

| 类别 | 用途 | 建议值 |
|------|------|--------|
| 外层背景 | 应用最外层机身背景 | `#0D0F11` |
| 项目栏背景 | 第一列导航背景 | `#14181C` |
| 对话框背景 | 第二列对话区域背景 | `#191C21` |
| 工作区背景 | 第三列工作区背景 | `#1C2026` |
| 面板底色 | 普通面板背景 | `#26292E` |
| 面板抬升色 | hover / active / 当前标签抬升底色 | `#2C3038` |
| 默认边框色 | 分隔线、面板边框、列表边界 | `rgba(241, 234, 223, 0.12)` |
| 激活边框色 | 当前标签、当前列表项、焦点面板边界 | `rgba(211, 154, 66, 0.58)` |
| 主文本 | 主要标题与正文 | `#F1EADF` |
| 次文本 | 次级说明与元信息 | `#B8B0A4` |
| 弱文本 | 辅助信息与低优先级元信息 | `#A49C90` |
| 主强调色 | 当前标签、主操作、当前焦点 | `#D39A42` |
| 主强调 hover | 主强调悬停态 | `#E0AA56` |
| 强调面文字色 | 主强调底按钮与高亮块内文字 | `#111315` |
| 文本选区背景 | 文本选中高亮 | `rgba(211, 154, 66, 0.32)` |
| 成功色 | 完成、已落盘、通过 | `#6F9D7A` |
| 警告色 | 等待处理、需关注 | `#C87533` |
| 危险色 | 阻塞、失败、冲突 | `#B76565` |

### 配色原则

- 主强调色只允许有一套，不得再引入默认蓝、默认紫或多主色并存
- 状态色只用于标签、状态点、细边框和局部提示，不得大面积铺底
- 主强调底上的文字必须统一使用深色文字色，禁止混用浅色文字
- 文本选区不得回退为浏览器默认蓝色
- 文字对比必须优先保证右侧内容可读性，不允许出现“亮底浅字”或“暗底灰字过弱”的问题
- 各列背景色必须有清晰但克制的层级差异，避免整页一片黑或整页一片灰

### 色温与层级要求

- 机身、列背景与面板背景整体应保持暖深色倾向，不得回退为明显偏蓝的冷科技色
- 最外层机身与最亮面板之间应拉开足够亮度差，形成桌面器物的层级断面
- 面板底色与面板抬升色必须保持同一色温家族，抬升态只提高亮度和边界，不改变整体材质倾向

### 派生色关系

- 激活边框色是主强调色的半透明派生色，建议按 `--color-accent` 的 `0.58` 透明度生成
- 若运行环境允许，可使用 `color-mix()` 或等价方式从主强调色派生
- 若为兼容性或一致性需要，也可直接落为固定 rgba 值，但语义上仍视为主强调色派生项

## 视觉规范

### 明暗与阴影体系

#### 设计原则

桌面质感必须通过阴影与高光建立。没有阴影，界面会退化为平面网页；阴影失控，则会退化为廉价拟物。因此应使用分层、克制、统一的阴影体系。

#### 阴影层级

| 层级 | 用途 | 建议值 |
|------|------|--------|
| 机身阴影 | 应用整体悬浮于桌面背景 | `0 18px 48px rgba(0, 0, 0, 0.42)` |
| 面板阴影 | 面板从背景中浮起 | `0 10px 24px rgba(0, 0, 0, 0.22)` |
| 控件阴影 | 当前标签、当前列表项、主按钮的轻微抬升 | `0 4px 12px rgba(0, 0, 0, 0.18)` |

#### 实施注记

`--shadow-shell` 是机身阴影的语义 token，不等同于普通 CSS 外阴影。在 Tauri 中，WebView 内部的 CSS 无法把阴影投射到操作系统桌面层，因此应用整体“悬浮于桌面”的效果应优先由窗口层实现，例如在 `tauri.conf.json` 或等价窗口配置中启用系统阴影与透明窗口能力。CSS 层只负责机身内部层级和面板阴影，不承担真正的系统级外投影。

#### 内高光

面板、输入区和当前标签应带有极轻的顶部内高光，用于模拟磨砂金属表面的受光效果。

建议值：

```css
inset 0 1px 0 rgba(255, 255, 255, 0.05)
```

#### 使用规则

- 页面级阴影只出现一次，用于建立整机压感
- 面板阴影用于面板与背景分离，不得层层叠加
- 列表项 hover 可以抬升，但不应形成明显漂浮卡片
- 当前标签和主按钮允许具备轻微“压上来”的效果
- disabled 态不参与抬升阴影变化

#### 材质纹理

“磨砂金属”不应只靠纯色块表达。面板类元素应统一叠加极轻微噪点纹理层，以建立材料颗粒感。

建议规则如下：

- 使用共享噪点资源，例如 `200 × 200` 的噪声 `SVG` 或 `PNG`
- 建议统一存放于 `app/assets/noise/` 或等价目录，禁止页面私带各自纹理资源
- 以绝对定位叠加到面板材质层之上
- `opacity` 建议为 `0.02 - 0.03`
- `pointer-events: none`
- 纹理层必须位于面板圆角裁切容器内部，与 `border-radius + overflow: hidden` 同层级配合，避免四角露出未裁切纹理边缘
- 不参与交互、不影响内容可读性，只作为表面颗粒层

若缺失该纹理层，则“磨砂”仅为命名描述，不构成实际材质效果。

工程落地上，噪点纹理定义为增强项而非阶段一阻塞项：

- 阶段一到阶段三可先以暖深色面板、内高光与阴影层级建立基础器物感
- 噪点纹理最迟应在阶段四或最终 polish 阶段接入
- 若列表性能、GPU 占用或跨平台渲染稳定性出现问题，可暂时关闭纹理层，但不得以此回退主题色、内高光和阴影体系

### 布局秩序

#### 列宽策略

主界面仍保持三列结构，但需采用更符合桌面工作台的列宽分配。为避免实现时再次拍值，本方案直接使用单值宽度：

| 区域 | 建议宽度 |
|------|----------|
| 项目栏 | `200px` |
| 对话框 | `344px` |
| 工作区 | 剩余全部空间 |

#### 滚动规则

- 页面外层不得出现整体滚动条
- 滚动只允许发生在列内或面板体内
- 列头、列尾、标签栏应保持稳定，不因内容滚动而整体位移

#### 分界规则

- 三列之间必须有清晰分界，可通过分隔线、阴影落差与背景差异联合表达
- 工作区内的标签栏与内容区必须有明确层级断点
- 左右列表与详情区应共享同一分割逻辑，不得每个标签页使用不同版式语言

建议技术形式如下：

- 基础分隔线使用 `border-right: 1px solid var(--color-border-default)` 或等价边框
- 分界内高光使用 `inset -1px 0 0 rgba(255,255,255,0.03)` 或等价实现
- 列级分界必须同时具备暗侧边界与亮侧轻微高光，不能只保留单根分隔线

#### 最小窗口尺寸

由于本应用采用三列桌面工作台结构，本轮设计必须定义最小窗口尺寸，避免窗口缩小时布局关系失真。

| 维度 | 建议值 |
|------|--------|
| 最小宽度 | `1280px` |
| 最小高度 | `800px` |

#### 小于最小尺寸时的处理

- 本轮不支持小于最小窗口尺寸的自适应压缩布局
- Tauri 窗口层应限制最小尺寸，不允许将窗口继续缩小
- 若未来需要支持小窗口或移动端，必须单独形成新的界面方案，不得在本方案基础上临时挤压三列结构

### 栅格、间距与圆角

#### 间距体系

统一采用 `4px` 基线，所有间距只能从以下档位中选择：

- `4px`
- `8px`
- `12px`
- `16px`
- `20px`
- `24px`

禁止出现无法归属上述体系的“凭感觉尺寸”。

#### 间距使用建议

| 层级 | 建议值 |
|------|--------|
| 极小间距 | `4px` |
| 标签与小元信息间距 | `8px` |
| 列表项内部主次信息间距 | `12px` |
| 面板内默认内边距 | `16px` |
| 大区块与大区块之间 | `20px` |
| 页面关键结构缓冲区 | `24px` |

#### 圆角体系

| 元素 | 建议值 |
|------|--------|
| 大面板 | `10px` |
| 输入框、列表项、按钮 | `8px` |
| 标签页与小型控件 | `6px` |
| 圆角标签 | `999px` |

圆角不应过大，否则会产生明显网页卡片感。

#### Token 对应值

为避免实现时再次拍值，圆角与相关尺寸 token 固定如下：

- `--radius-panel: 10px`
- `--radius-control: 8px`
- `--radius-tag: 6px`
- `--radius-pill: 999px`
- `--size-status-dot: 6px`

### 文字体系

#### 字体方向

字体策略必须覆盖 Windows、macOS 与 Linux，不能只按 Windows 字体思路定义。

#### 跨平台字体分支

建议按平台分支组织：

```text
Windows:
Segoe UI Variable, Microsoft YaHei UI, Segoe UI, Microsoft YaHei, sans-serif

macOS:
SF Pro Text, PingFang SC, Helvetica Neue, sans-serif

Linux:
Noto Sans, Noto Sans CJK SC, Source Han Sans SC, sans-serif
```

#### CSS 落地方式

建议通过运行时平台检测为根节点写入 `data-platform` 属性，再由 CSS token 分支承接，不在页面局部直接写死字体族。

建议机制如下：

- 应用启动时在顶层入口检测平台
- 将结果写入 `<html data-platform="windows|macos|linux">`
- CSS 根据属性选择字体 token

若运行于 Tauri 环境，优先使用 Tauri 平台 API 或 `@tauri-apps/plugin-os` 检测；若运行于普通浏览器开发环境，则允许退回到 Web 平台检测并使用默认字体栈。

若阶段一暂未接入 Tauri 平台检测，则允许短期退化为静态跨平台字体栈；但在最终验收前必须补齐 `data-platform` 机制，避免各平台字体表现失控。

基础默认值建议为：

```text
Segoe UI Variable, SF Pro Text, PingFang SC, Microsoft YaHei UI, Noto Sans CJK SC, sans-serif
```

#### 字号层级

为避免实现时再次拍值，字号直接拍定为单值：

| 层级 | 用途 | 建议值 |
|------|------|--------|
| 焦点标题 | 当前项目名、当前详情标题 | `20px` |
| 区块标题 | 标签内容区小节标题 | `16px` |
| 正文 | 常规内容与列表主文字 | `13px` |
| 辅助文字 | 时间、状态说明、弱元信息 | `12px` |
| 极小标注 | 紧凑标签、单行元信息、状态短语 | `11px` |

#### 文本规则

- 主要文字必须始终有足够对比度
- 次级文字只负责说明，不得反客为主
- 弱文字只用于时间、路径、状态辅助等低优先级信息
- 不允许同一屏中出现过多字号等级
- `11px` 只允许用于紧凑标签、单行 meta、状态短语，不得用于正文段落、详情正文和可换行说明文本
- 项目名、标签名、列表主标题、路径等单行高频信息默认使用单行截断与省略号
- 详情文本、消息正文、日志详情默认允许换行，不使用强制截断

#### 行高与字距

不同文字层级必须使用固定行高与字距，禁止页面局部自行调整。

| 层级 | 行高 | 字距 |
|------|------|------|
| 焦点标题 | `1.3` | `0.01em` |
| 区块标题 | `1.4` | `0.02em` |
| 正文 | `1.4` | `0.01em` |
| 辅助文字 | `1.3` | `0.02em` |
| 极小标注 | `1.2` | `0.04em` |
| 中文标签、按钮、标签页文案 | `1.25` | `0.05em` |

中文小字号 UI 文案应适度增加字距，避免在 `12px - 13px` 尺度下显得拥挤粗糙。

#### 字重

字重必须统一，不得由页面局部自行决定。

| 层级 | 字重 |
|------|------|
| 焦点标题 | `600` |
| 区块标题 | `500` |
| 正文 | `400` |
| 辅助文字 | `400` |
| 极小标注 | `500` |
| 按钮 / 标签页文案 | `500` |
| 项目栏项目名 | `500` |

#### 文本渲染

建议全局启用更接近桌面应用的文本渲染策略：

- `-webkit-font-smoothing: antialiased`
- `-moz-osx-font-smoothing: grayscale`
- `text-rendering: optimizeLegibility`

#### 对比度目标

本方案默认遵循 WCAG 2.1 AA 级别作为最低要求。

- 所有 `13px` 及以下正文与辅助文字，对比度不得低于 `4.5:1`
- 所有 `14px` 以上且非加粗的大文字，对比度不得低于 `3:1`
- 焦点环、边界高亮与状态标签，在深色背景上必须清晰可辨，不得依赖模糊发光补足可见性

#### 色板校验示例

基于本方案建议色板，以下组合满足小字 AA 目标：

- `#F1EADF` on `#191C21` 约为 `14.30:1`
- `#B8B0A4` on `#191C21` 约为 `7.96:1`
- `#A49C90` on `#191C21` 约为 `6.29:1`

原先较暗的弱文本色若低于 `4.5:1`，不得继续使用于小字号文本。

### 动效与交互反馈

#### 设计原则

动效用于建立桌面软件的压感、切换感与响应感，不用于制造表演性动画。所有动效必须短、稳、克制。

#### 标准时序

| 层级 | 用途 | 建议值 |
|------|------|--------|
| 快速反馈 | hover、focus、列表项状态变化 | `120ms` |
| 常规切换 | 标签页切换、按钮压感、面板抬升 | `180ms` |
| 结构变化 | 抽屉展开、局部折叠、信息块显隐 | `240ms` |

#### 缓动曲线

建议只保留两条曲线：

- 标准界面曲线：`cubic-bezier(0.2, 0.8, 0.2, 1)`
- 快速压感曲线：`cubic-bezier(0.22, 1, 0.36, 1)`

#### 应用规则

- 列表项 hover 只做轻微底色、边框和阴影过渡
- 标签页切换只做抬升与文字提亮，不做滑块炫动，并统一使用 `--ease-standard`
- 输入框 focus 只做边框与焦点环变化，不做夸张呼吸动画
- 禁止使用超过 `240ms` 的主界面过渡
- `--ease-snappy` 仅用于按钮按压、列表项压下等“压感类反馈”，不用于标签切换和面板抬升

#### 激活压感

点击与按压反馈必须具备明确的下压感，不能只依靠底色变化。

- 按钮、标签页、列表项在 `:active` 时应产生轻微下压位移
- 建议值：`transform: translateY(1px)`
- 禁止使用过大的缩放或位移，避免产生玩具化弹跳感
- `:active` 不得覆盖或移除既有的 `:focus-visible` 焦点环
- 若元素同时命中 `:focus-visible` 与 `:active`，焦点环继续保留在外层，位移仅作用于元素本体或其内层承载面
- 不允许通过 `overflow: hidden`、额外包裹层裁切或 transform 叠加，导致键盘焦点环在按压态消失

#### 降低动效（Reduced Motion）

当系统级 `prefers-reduced-motion: reduce` 生效时：

- 所有过渡 duration 应降至 `0ms` 或 `1ms`
- easing 应退为 `linear`
- 禁止保留位移、缩放或渐变强调类动画，仅保留必要的状态切换

### 焦点、选区与滚动反馈

#### 焦点环原则

桌面软件必须对键盘导航可见。所有可交互元素都必须具备统一焦点环，不得依赖浏览器默认样式，也不得完全移除 focus 指示。

#### 触发机制

- 焦点环统一基于 `:focus-visible` 实现
- 禁止将主焦点环绑定到 `:focus`，避免鼠标点击时出现过量视觉噪音
- 鼠标交互可保留 hover / active / selected 反馈，但不展示键盘焦点环

#### 焦点环样式

| 属性 | 建议值 |
|------|--------|
| 颜色 | `#D39A42` 的半透明外环 |
| 宽度 | `2px` |
| 外扩 | `2px` |
| 阴影 | `0 0 0 1px rgba(17, 19, 21, 0.9)` 作为内衬分隔 |

#### 面板级焦点感知

当键盘焦点进入面板内部时，面板容器本身应通过 `:focus-within` 进入弱激活态。

- 面板容器边框应轻微提亮
- 建议使用 `--color-border-active` 的低透明度版本
- 仅用于帮助用户在三列与多面板环境中定位当前键盘工作区域，不替代具体控件的焦点环

#### 文本选区

必须重置浏览器默认蓝色选区。

- 使用 `::selection`
- 背景采用 `--color-selection-bg`
- 文字保持当前文字色或与当前文字色等价的高可读状态

浏览器默认蓝色选区会强烈暴露 Web 页痕迹，属于必须消除的桌面感破坏项。

#### 滚动条规范

滚动条属于桌面观感的一部分，不得完全交给浏览器默认样式。整页禁止滚动，但列内与面板体内滚动条必须可感知、不过度抢眼。

| 属性 | 建议值 |
|------|--------|
| 宽度 | `8px` |
| 高度 | `8px` |
| 拇指颜色 | `rgba(184, 176, 164, 0.42)` |
| 悬停颜色 | `rgba(211, 154, 66, 0.55)` |
| 圆角 | `999px` |
| 轨道 | 透明 |

- 滚动条默认可见但低存在感
- 悬停或拖动时颜色增强
- 不允许出现浏览器默认亮色滚动条
- 项目栏、对话框、工作区详情区必须共享同一滚动条样式
- 所有可滚动容器应启用 `scrollbar-gutter: stable` 或等价策略，避免内容因滚动条出现与消失发生横向跳动

滚动条布局稳定与滚动条外观不是同一问题，不应被视为二选一：

- `scrollbar-gutter: stable` 负责布局稳定，防止内容横向跳动
- `scrollbar-width` / `scrollbar-color` 负责标准属性层的宽度与颜色表达
- `::-webkit-scrollbar` 及相关伪元素作为 WebKit / Tauri WebView 的外观适配层

在 Tauri 场景中，允许采用“标准属性 + WebKit 伪元素”的双层策略；若某平台不支持其中一层，应优雅降级而非混乱叠加。

### 禁用（Disabled）状态

#### 原则

disabled 是独立状态，不得通过“像是没选中”来含混表达。其目标是明确告知不可交互，同时保持内容仍可辨认。

#### 样式规则

| 元素 | 规则 |
|------|------|
| 按钮 | 不透明度降至 `0.45`，取消抬升阴影，`cursor: not-allowed` |
| 输入框 | 不透明度降至 `0.55`，背景略变暗，保留文本可读性 |
| 列表项 | 不进入 hover / active 抬升态，文本与状态信息降噪但仍可识别 |

#### 交互规则

- disabled 元素不得触发 hover 强化
- disabled 元素不得显示焦点环
- disabled 元素不得响应键盘激活与鼠标点击
- disabled 态文本仍需满足可辨识要求，不得通过极低透明度直接“做没”

### 状态表达规则

#### 状态优先级

状态表达优先采用以下顺序：

- 位置变化
- 边框变化
- 底色轻微抬升
- 标签色
- 状态点

不得将状态表达主要建立在大面积彩色铺底上。

#### 状态样式要求

- `完成` 使用低饱和绿色，仅用于标签、点或极小边框
- `等待处理` 使用低饱和琥珀色
- `阻塞 / 冲突 / 失败` 使用低饱和暗红色
- `当前焦点` 使用主强调色，但仅局部使用

## 界面部件规范

### 项目栏

项目栏是项目切换区，不是摘要展示区。

- 采用窄栏、紧凑、高密度设计
- 每个项目项以“名称 + 状态点 + 极小元信息”构成
- 不显示大段描述、不显示夸张进度条
- 当前选中项必须具备明显但克制的压感与边界增强
- 整体观感应接近 IDE 侧栏或数据库工具的导航树，而不是内容卡片列表
- 状态点尺寸固定为 `6px`

### 对话框

对话框仍然是对话框，不改变其产品定义。

- 整体呈现桌面软件内建聊天面板的样式，而非社交产品或网页 IM 样式
- 消息块采用更紧凑、更结实的短矩形样式，弱化松软气泡感
- 用户消息与助手消息通过边框、底色与细节差异区分，不通过大面积高饱和色区分
- 顶部项目信息、阶段标签、蓝图焦点信息应降噪处理，不抢主消息内容
- 输入区应表现为稳定的输入托盘，具备内阴影、顶部边线与明确的可输入表面

### 标签页

工作区标签页应表现为桌面应用的工作标签，而非网页 pill tab。

- 标签与工作区框架为一体化结构
- 当前标签具备抬升感，非当前标签处于沉下状态
- 标签之间保持紧凑排列，不使用夸张胶囊造型
- 标签选中状态由底色抬升、边界提亮和阴影轻微增强共同表达

### 列表区

蓝图条目列表、任务树列表、日志事件列表应共享统一列表语言。

- 列表项高度紧凑，但需保持可点击性
- 紧凑列表项最小高度不得低于 `40px`
- 列表项 hover、active、selected 采用一致的状态切换方式
- 列表项内部结构必须统一为“主信息在上，弱元信息在下”
- 状态标签、进度数字、负责人等元信息应沿同一视觉节奏排布

### 详情区

详情区不应呈现一堆网页卡片，而应表现为属性检查器式的分组面板。

- 每个信息分组都使用同一类面板样式
- 面板内以“标签名 + 内容”方式组织，不使用夸张标题条
- 关键数字可以稍作放大，但不应破坏整体节奏
- 详情区各面板之间的关系应表现为同一工作区内部的检查块，而非独立内容卡片

### 输入控件与按钮

- 输入框应具备桌面托盘感与内凹感
- 主按钮采用琥珀铜强调，承担明确主操作
- 主按钮文字统一使用 `--color-text-on-accent`
- 次按钮使用更克制的深色面板样式
- 标签与按钮的形状区分需清晰，避免一切都长得像 pill

### 输入框错误（Input Error）状态

输入框作为基础界面部件，必须定义错误态。

- 输入框 error 态边框切换为 `--color-danger`
- 输入框 error 态焦点环应使用危险色半透明外环，而非继续使用默认焦点环颜色
- 错误提示文本使用危险色，但字号仍遵循辅助文字层级，不得额外放大
- error 态与 disabled 态不可叠加为含混状态；若同时出现，以 disabled 为交互状态、以错误提示为信息状态分别表达

## 实现架构与样式承接

### 总体决策

本次视觉体系不再通过 Nuxt UI 主题覆盖实现，不再依赖 `app.config.ts` 中的 `ui.colors`、`ui.card`、`ui.button` 等扩展点承接视觉风格。Nuxt UI 退出本轮视觉实现路径，前端界面改由“自定义主题 token + Tailwind 布局 + 自研基础界面部件”承接。

### 组件层承接方式

组件层采用自研基础界面部件，不再使用 Nuxt UI 的通用外观组件作为壳层。

基础界面部件包括但不限于：

- `Panel`
- `Tabs`
- `Tag`
- `Composer`
- `ListRow`
- `Button`
- `Input`

这些部件仅承接视觉结构与状态样式，不承接业务语义。业务组件必须由这些基础界面部件组合而成，不得在页面内部重新定义一套局部样式体系。

Nuxt UI 的保留与替换策略必须明确如下：

- 壳层、工作区、项目栏、对话框、标签页、列表、详情区所使用的可见外观组件，最终必须全部切换为自研基础界面部件
- 若过渡期仍保留 `@nuxt/ui` 模块或少量 `<U*>` 组件，它们不得继续出现在主界面壳层与工作区主路径中
- `app.config.ts` 不再承担视觉主题职责，只允许保留最小兼容配置
- 若任一核心路径仍依赖 Nuxt UI 默认外观样式，则该路径视为尚未完成视觉体系迁移
- 若暂未移除 `@nuxt/ui` 依赖，应将其视为运行时依赖而非视觉主题依赖；禁止再通过 Nuxt UI 默认 token、默认蓝色状态和默认组件外观承接主界面视觉
- `UButton`、`UCard`、`UTabs`、`UInput`、`UTextarea` 等自带可见外观的组件，不得直接暴露在项目栏、对话框和工作区主路径中；若短期无法移除，必须先包裹为自研基础界面部件并切断默认外观
- 过渡期允许保留的仅应是对视觉无主导权的基础运行能力，不允许留下“先继续用 Nuxt UI 默认样式，后面再覆盖”的实施路径

### 基础界面部件样式归属

基础界面部件的核心外观规则应统一落在全局样式体系中，不应依赖 `style scoped` 形成局部优先级覆盖。

- `Panel`、`Tabs`、`Tag`、`Composer`、`Button`、`Input` 等基础界面部件使用全局语义类名承接外观
- `style scoped` 只允许用于业务组件的局部排版微调，不允许重新定义基础界面部件的颜色、边框、阴影、圆角与动效
- 若某业务组件需要特殊外观，必须先回到基础界面部件层或语义类层扩展，不得在页面内通过 scoped 样式覆盖主系统

### 样式承接方式

样式分三层承接：

- 主题 token：通过 CSS 自定义属性定义颜色、阴影、圆角、动效、滚动条与焦点环
- 布局与尺寸：通过 Tailwind CSS 承接栅格、弹性布局、宽高、间距等原子能力
- 组件外观：通过基础界面部件内部类名和语义类名承接

禁止页面直接写十六进制颜色、临时阴影值、局部圆角值和页面私有动效值。

### Tailwind 与 token 集成策略

本方案采用单一策略，避免两套写法并存：

- Tailwind 仅承接布局、尺寸、弹性、栅格、定位与基础间距
- 颜色、边框、阴影、圆角、动效、焦点环全部通过 CSS token 与语义类名承接
- 页面层禁止大量使用 `bg-[var(...)]`、`text-[var(...)]`、`border-[var(...)]` 这类 arbitrary value 拼装视觉

换言之，Tailwind 不承担视觉主题语义，不在 `tailwind.config` 中扩展一套颜色命名，也不允许页面局部直接拼 arbitrary value 形成第二套视觉体系。视觉实现统一沉到：

- token
- 基础界面部件
- 语义类名

只有极少数一次性实验或过渡代码可以临时使用 arbitrary value，进入正式实现前必须下沉为 token 或语义类。

### 基础交互规则

#### user-select

- 正文内容、消息内容、日志文本、路径文本允许文本选择
- 按钮、标签页、标签、项目项标题栏等纯操作型控件默认 `user-select: none`

#### 光标语义

桌面应用中的光标语义应与网页区分，不允许把所有可点击区域都处理为 `pointer`。

| 元素类型 | 光标 |
|----------|------|
| 导航控件（项目项、标签页、列表项） | `default` |
| 主操作按钮、对话类按钮、明确操作按钮 | `pointer` |
| 可编辑区 | `text` |
| 拖拽分隔线 | `col-resize` |
| disabled | `not-allowed` |

静态信息区保持默认光标，不得滥用 `pointer`。

### 建议落点

建议样式资源按以下结构收敛：

- `app/assets/css/tokens.css`
- `app/assets/css/base.css`
- `app/assets/css/components.css`
- `app/assets/css/main.css`

其中：

- `tokens.css` 负责定义 token
- `base.css` 负责根字体、滚动条、焦点环与全局重置
- `components.css` 负责基础界面部件外观
- `main.css` 仅负责组织导入，不承担主要设计逻辑

如短期内不拆文件，亦必须在单文件内部按上述层级分区组织，不允许 token、base、component 样式交叉混写。

## 实施建议

### 阶段划分

#### 阶段一：Token 与根层重建

输入：

- 现有 `main.css`
- 本文档的色板、尺寸、动效与排版规则

输出：

- 完整 token 文件
- 平台字体切换机制
- 根层文本渲染、滚动条、选区、焦点环与 reduced motion 规则
- 旧冷蓝值清理清单与替换映射

最低完成条件：

- token 参考表全部落地
- 根层不存在裸十六进制颜色值
- `:focus-visible`、`::selection`、`scrollbar-gutter` 已启用
- 已建立当前遗留冷蓝值的清理清单，并明确替换到新 token 的承接关系

#### 阶段二：壳层与三列机身重建

输入：

- 阶段一 token
- 当前三列布局与壳层组件

输出：

- 三列固定宽度壳层
- 列间立体分界
- 窗口层最小尺寸与 Tauri 阴影配置

建议配置片段：

```json
{
  "app": {
    "windows": [
      {
        "minWidth": 1280,
        "minHeight": 800,
        "shadow": true
      }
    ]
  }
}
```

若浏览器开发环境无法模拟窗口最小尺寸，则以前端调试约束代替，但最终验收以 Tauri 窗口层配置为准。
当前项目的落点文件应为 [src-tauri/tauri.conf.json](/E:/Repositories/projects/Zoranner/workflow-suite/docwise-ai/docwise/src-tauri/tauri.conf.json)。前端 CSS 无法替代该窗口层约束，因此 `minWidth`、`minHeight` 与 `shadow` 必须在该配置文件或等价 Tauri 窗口构建路径中完成。

最低完成条件：

- 项目栏与对话框宽度收敛到单值
- 列间边界具备“分隔线 + 内高光”
- 页面外层无滚动条

硬依赖：

- 必须在阶段一完成后进行

3. 再做基础界面部件

### 验收标准

满足以下条件时，可认为视觉体系重构完成：

- 所有颜色、阴影、圆角、焦点环、动效均来自统一 token 或基础语义类承接，正式源码中不存在裸十六进制颜色值、局部阴影值与 page-local 圆角值
- 主界面核心路径不再残留旧冷蓝值与默认科技蓝状态，尤其不得继续出现 `#0B1120`、`#0D1422`、`#0B1320`、`#0F1726`、`#141D2D`、`#192335`、`#101827`、`#3B82F6`、`#1D4ED8`、`#2563EB`、`#93C5FD`、`#BFDBFE`、`rgba(37, 99, 235, *)`、`rgba(148, 163, 184, *)` 及其等价冷蓝或灰蓝透明值
- 所有可滚动区域仅存在列内或面板体内，页面外层无滚动条
- 所有间距取值均属于 `4 / 8 / 12 / 16 / 20 / 24` 体系
- 所有 `13px` 及以下文本对比度均达到 `4.5:1` 或以上
- 所有可交互元素都通过 `:focus-visible` 呈现统一焦点环，鼠标点击不触发该焦点环
- 所有导航控件使用 `cursor: default`，主操作按钮使用 `cursor: pointer`
- 操作型控件默认启用 `user-select: none`
- 全局已启用文本渲染 antialiasing 策略
- `::selection` 已重置为琥珀系选区，不再出现浏览器默认蓝色高亮
- 若性能与稳定性验证通过，面板类元素应存在统一噪点纹理层，且纹理位于圆角裁切容器内部；若本轮因性能、GPU 占用或跨平台渲染差异暂缓接入，必须留下明确豁免记录，且不得回退暖深色、内高光与阴影层级
- 项目栏、对话框、工作区标签页、列表项、详情块均使用同一套基础界面部件语言
- 应用窗口被限制为不小于 `1280px × 800px`
- 项目栏宽度为 `200px`，对话框宽度为 `344px`
- 焦点标题、区块标题、正文、辅助文字、极小标注均使用固定字号与字重
- 任意两个标签页之间切换时，外观语言连续，不出现页面级风格断裂

## 结论

Docwise 前端本轮需要的不是局部微调，而是彻底的视觉系统重建。重建的核心不在于“更像某个网页模板”，而在于建立一套面向桌面软件的统一判断标准：有机身、有面板、有压感、有材质、有秩序。

在该前提下，项目栏、对话框、工作区不会被重新定义为其他产品形态，而是在既有功能边界内，获得一致、稳定、具有本地软件质感的最终外观。
